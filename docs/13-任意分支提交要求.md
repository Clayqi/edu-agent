# 任意分支提交要求（给所有组员）

> 场景：你在自己机器上把一件事做通了（装了外部依赖、跑了别人的脚本、写了个新功能、修了个 bug），
> 现在要把它交进仓库。
> 结论：**你本地的「环境」没法发给我**——依赖装在应用里、`node_modules` 是你机器上编译出来的、
> 路径写死在你机器上。所以要交的从来不是文件，而是三样：
> **代码走 PR + 做法写成步骤 + 证据留档**。
>
> 适用范围：**任意分支、任意任务**（功能 / 修复 / 集成 / 脚本 / 文档）。
>
> 本文由 `docs/09-WPS接入交接要求.md` 抽出来——那份是 2026-09-11 为 WPS MCP 接入写的**具体案例版**
> （三样交付物 + 当时的验收动作，仍有参考价值）；本文是**通用版**，把「交接」推广成「任何分支的提交」。
> WPS 的技术细节见 `docs/08-WPS集成说明.md`（安装 / 开关 / 导出原理）与 `tools/wps_spike/README.md`（从零复现）。
>
> 仓库：<https://github.com/Clayqi/edu-agent> ｜ 流程细则见 `docs/03-团队协作与版本迭代.md`、`CONTRIBUTING.md`

## 一、交给评审人的三样东西（缺一样不算交付）

### 1) 代码 —— 走 GitHub 分支 + PR，不许发压缩包 / 微信截图

- 从最新 `main` 拉分支（命名见 `CONTRIBUTING.md` §一）：

  ```bash
  git fetch origin
  git checkout -b feat/<模块>-<内容> origin/main     # 或 fix/<模块>-<内容>、hotfix/<内容>
  ```

- **只提交这件事该改的东西**：新模块 + 它的测试 + （需要时）安装/启动脚本。
  别顺手改别人的模块；热点共享文件（`README.md`、`static/index.html`、`web_server.py`、`prompts.py`）
  动手前先 `git pull --rebase origin main`。
- 推分支 → 开 PR：
  `https://github.com/Clayqi/edu-agent/compare/main...<你的分支名>?expand=1`
  PR 里写清 **改了什么 / 怎么验的 / 有没有动别人的模块**；合并用 **Squash and merge**。
- **禁止直接向 `main` 推提交**（`CONTRIBUTING.md` §一）。
- **第三方源码与构建产物绝不入库**：外部依赖（`node_modules`、编译产物、几百个文件的上游仓库）
  一律由安装脚本克隆到**仓库外**，仓库里只留**适配层 + 安装脚本 + `.gitignore` 护栏**。
  先例：WPS 的 `wps-skills` —— 护栏见 `.gitignore` 里的 `mcp_servers/wps-office-mcp/`、`skills/` 两行。
- **不要提交本地产物**：`.env`、`data/`、`logs/`、`content/plans/`、`model_cache/`、`*.bak-*`。

### 2) 环境 / 做法 —— 写成「从零复现步骤」（因为没法打包）

新建或补全一份文档（放 `docs/` 或 `tools/<你的主题>/README.md`），必须包含：

| 项 | 要写什么 |
|---|---|
| 我的环境 | 操作系统版本 / 相关应用版本号 / 运行时版本 / 外部依赖锁定的 commit（在依赖目录里跑 `git rev-parse HEAD`） |
| 从零步骤 | 每条命令原样贴：装依赖 → 构建 → 必要的手工步骤 → 启动 → **我调了什么、传了什么参数、返回什么原文** |
| 踩过的坑 | 遇到什么问题、怎么解决的、为什么这么绕（**这部分最值钱，别省**） |
| 一句话风险 | 换台机器复现最容易卡在哪里 |
| 边界 | 这份东西**不做什么**（免得别人以为它覆盖了更多） |

### 3) 证据 —— 证明「真跑通了」，不是「我觉得能跑」

- 日志贴**原文**，别改写、别只贴结论行。
- 界面类改动的**截图**（带时间）。
- 数据类改动给可核对的东西（文件头字节、条数、`md5`、接口返回原文…）。
- 不允许出现「应该可以 / 大概能跑」。

### 自查（交付前自己先过一遍）

> 如果你把自己的机器格式化了，还能照着这份文档再搭起来吗？不能，就说明没写全。

## 二、评审人的验收动作（三个都不能省）

1. **看 PR 范围**：改动的文件是不是**只有这件事该动的**？有没有顺手改 `src/`、`tests/`、`static/`？
   有没有把第三方代码或大文件塞进来？——`git diff --stat origin/main...<分支>` 一眼能看出。
2. **在自己的机器上照文档从零走一遍**：走得通 = 真交付；走不通 = 补步骤。
   （这步不能跳，否则合并的是「你说你能跑」，不是「它真的能跑」。）
3. **确认版本锁**：文档里有没有外部依赖的 commit 号？以后上游改了接口，我们得知道当初锁的是哪一版。

---

## 三、提交前自查清单（硬规则）

| 检查 | 怎么做 |
|---|---|
| 测试全绿 | `.venv/Scripts/python.exe -m unittest discover -s tests -p "test_*.py"` → `OK`。**改测试来「过」= 不合格** |
| 没有盘符绝对路径 | `grep -rn "[A-Z]:[\\/]" --include='*.py' --include='*.cmd' --include='*.ps1' --include='*.html' src scripts deploy static`（应无输出，见 `CONTRIBUTING.md` §2之二） |
| 没有本地产物 | `git status --short` 不应出现 `.env` / `data/` / `model_cache/` / `*.bak-*` |
| `chroma_db/` 假脏 | 只要读过向量库它就会显示 `M`（内容没变）：`git checkout -- chroma_db/` 丢弃 |
| 热点文件先 rebase | `README.md` / `static/index.html` / `web_server.py` / `prompts.py` 改过就先 `git pull --rebase origin main` |
| 提交消息 | `type(模块): 做了什么，为什么` |
| 第三方依赖 | 有没有混进仓库？（`.gitignore` 护栏在不在） |

## 四、第三方依赖与版本锁（最容易漏的一条）

| 问题 | 为什么要问 |
|---|---|
| 依赖装在哪？ | **绝不能装进仓库目录**；已经装进来了就必须确认它在 `.gitignore` 里、绝不会被 `git add`（几百个文件 + `node_modules` 会让仓库爆掉） |
| 锁的是哪一版？ | 文档里写 commit 号；上游改接口时，我们才知道当初对齐的是哪一版 |
| 是「跑通了一个工具」还是「接进 edu-agent 代码里了」？ | 前者交**文档 + 证据**；后者才需要 **PR**。两者交付物不一样，别混 |

## 五、万能任务模板（以后任何任务都能套）

```
1) 目标：这次做的是什么，做到什么程度算完（不做什么也要写清）
2) 边界：只准新建/修改 <清单>；严禁修改 <清单>
3) 步骤：每条具体到命令
4) 交付物：三样 —— 代码(分支+PR) / 步骤文档 / 证据(日志+截图)
5) 验收标准：什么算通过（必须是可验证的实物，不接受"应该可以"）
6) 时限：几点前给结论；卡住多久必须上报
7) 给 AI 的原话：单独一段，人和 AI 的要求分开写
```

## 六、附：给 AI 助手的原话模板（复制给你的 AI）

```
只准新建/修改：<清单>；除 <清单> 外不得修改仓库里任何已有文件。
每执行一步，把真实命令和输出贴出来；不许说"已完成"而不给输出。
遇到报错就停下来告诉我，不要自己换方案，也不要改测试来迁就实现。
提交前必须跑：python -m unittest discover -s tests -p "test_*.py"，确认全绿（OK）；
不 OK 就回退你的改动，不要改测试。
不要提交 .env / data/ / 本地产物；不要把第三方源码或 node_modules 放进仓库。
```

## 七、一句话总结

**环境不能发文件，只能发步骤；代码必须走 PR；结论必须有证据。**
这三样交齐、评审人在自己机器上照着重做一遍能通，才算真交付。
